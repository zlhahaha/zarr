## Release implementation and verification

- Implemented v3 sharding-indexed layout parsing and native filesystem range reads. An element/region read fetches only the shard index (capped at 16 MiB) and selected encoded inner chunk (capped at 64 MiB), not the entire shard. Supports start/end indexes, little/big-endian index bytes, optional CRC32C, edge shards and absent inner chunks, then reuses the typed bytes/compression decoder. Sharded writes return `false`.
- Added four independent zarr-python 3.4.0 fixtures: 2D gzip with edge/absent chunks; start index with boundary shard; big-endian index/inner bytes without CRC; Blosc LZ4 inner chunks. Added CRC32C check-vector and malformed-index tests.

## P0 read resource budgets (2026-09-29)

- Implemented immutable shared `store.ReadLimits` for memory/native typed arrays and HTTP hydration: defaults 1 MiB metadata, 64 MiB encoded/decoded chunks, 64 MiB logical region bytes, 8388608 region elements, 16384 touched chunks, rank 64, JSON depth 64. All caps must be positive. Region count checks do not enumerate coordinates; typed preflight happens before result allocation. Native scratch views inherit explicit policies.
- Native `get` opens/stats the same handle and uses a fixed-length read, never unbounded read-to-EOF. Oversized file inputs raise `fs.ReadLimitExceeded`, including selected shard payloads before payload I/O, and never become missing-fill values. Invalid/budget-rejected typed opens/regions/codecs return `None`; existing OS exceptions still propagate. Consolidated openers accept policies. Raw memory-map access/direct codecs remain caller-managed.
- Constant-space JSON nesting checks precede UTF-8/JSON parsing on store/hierarchy paths. HTTP combines existing stricter caps with the shared policy and adds a 64 MiB default cumulative encoded hydration cap. Input/work caps are not total-RAM, deadline, concurrency, transactional or streaming guarantees.

## Single-key filesystem write safety — 0.5.0 (2026-09-29)

- Implemented exclusive sibling `.zarr-tmp-*` creation with bounded collision retry, complete data-synchronized staging, handle closure and `rename(replace=true)`. `FileStore::put` never truncates or deletes the destination as a replacement fallback; native chunks/metadata/attributes share the path. Concurrent parent creation tolerates an existing directory only.
- Acquisition/commit/cleanup use protected cancellation ownership boundaries. `errdefer` handles cleanup on errors and cancellation, including future cancellation semantics where ordinary `catch` does not intercept cancellation. A commit in progress can finish despite cancellation. Cleanup failure raises public `fs.WriteCleanupFailed(path, diagnostic)` and supersedes the original failure; no automated orphan deletion is performed.
- Added 14 regressions in `store/fs/write_wbtest.mbt` and `write_test.mbt`: partial writes/commit failures on existing/absent targets, retained closed staging handles, collisions/exhaustion, creation/cleanup failure, staging cancellation, cancellation during acquisition (including empty values), protected commit cancellation, real replacement failure, growing/shrinking/empty files, retained old reader handles, concurrent complete-key writers and partial multi-chunk failure. Updated `cmd/native_demo` to overwrite compressed chunks.
- Local native 116/116 and wasm-gc 58/58 tests passed. README, usage, resource budgets, benchmark limitations, roadmap and changelog now distinguish single-key visibility from multi-key transactions and power-loss durability. `docs/WRITE_SAFETY.md` documents recovery, identity/permission/symlink changes, disk space and exact failure outcomes. ## Working rules

- Treat README support claims as test-backed, not aspirational. Run `moon info && moon fmt`, inspect `.mbti` diffs, then native/wasm checks and tests after code changes; verify Python interoperability and CI for codec/storage changes.
- Preserve unrelated work and generated `integration/.roundtrip/` stores. Fixture generators refuse to overwrite existing stores; use new fixture names or validated, recoverable moves for regeneration.
- Commit coherent features; push verified work to `main` under the user's prior authorization. Do not force-push or submit contest materials. A new Mooncakes version must be requested and verified before publication; versions `0.1.0` through `0.7.0` are published and cannot be overwritten.
